## What this is

A plan for surfacing the schedule-quality work that lives in the
`scripts/scheduler_eval/` harness through the editor and viewer UIs.
The harness produces detailed per-pair, per-team, and per-fixture
quality data that today is only accessible via command-line runs.
End users (event organizers, team coaches) can't see most of it.

The plan is laid out in four tiers, ordered by effort and by
how much judgment work each one requires before shipping.

## What this is not

- **A scheduler-improvement workstream.** The scheduler itself is
  the subject of `workstreams/scheduler-quality.md` and the
  ongoing eval work. This doc is about *exposure* of measurements,
  not improvement of what's measured.
- **A redesign of the existing Schedule Quality card.** The card is
  effective at what it does. This work adds detail it currently
  hides and routes additional measurements through it.
- **A commitment to ship.** Captured here so a future session can
  pick it up; not started; no priority assigned.

## Current state — UI quality surfaces

### Editor (`static/index.html`)

| Surface                      | Location                                       | Purpose                                                |
|------------------------------|------------------------------------------------|--------------------------------------------------------|
| **Schedule Quality card**    | `#diversityReportCard` at `:2757`              | Headline tiles + histogram + issues                    |
| `loadDiversityReport()`      | `:4164`                                        | Fetches `/api/abstract-schedules/{id}/diversity-report` |
| `renderDiversityCard()`      | `:4220`                                        | Renders the card from server data + client state       |
| **Placement Criteria panel** | `#placementCriteriaPanel` at `:2623`           | Construction weights (configuration, not measurement)  |
| **Competition Approved**     | `#competitionApproved` at `:2649`              | Boolean + deviations list                              |
| **Quality Preset**           | `#qualityPreset` at `:2669`                    | Iteration budget (configuration, not measurement)      |

The Schedule Quality card is the only post-hoc quality measurement
surface. Its content:

1. Six headline tiles — Avg partner repeats, Avg opponent repeats,
   Pairs never met, Station balance, Back-to-backs, Surrogates.
2. Stacked-bar histograms for partner + opponent repeat
   distributions, color-coded zero / at-floor / over-floor /
   way-over-floor.
3. "Notable" issues section — counts only, no specifics.
4. Inline `<details>` help explaining what "pair" means.
5. Click-to-filter on B2B and Surrogate tiles.

### Viewer (`static/view.html`)

**Zero quality surfacing.** The viewer is intentionally minimal —
operational data only. Cycle-time stats panel
(`#statusCycleStats` at `:2334`), per-team stats grid (`.team-stats`
at `:1944`, fed by TBA), Statbotics link (`:4342`). Nothing about
diversity, repeat partners, station balance, or any aggregate
quality measurement.

### What the editor card does well

- **Floor-relative semantics, not threshold classification.** The
  card shows "X above the theoretical floor" rather than the
  harness's "poor / acceptable / near_optimal" labels. This avoids
  the harness's mis-calibrated thresholds (a 36×7 played schedule
  generated by MatchMaker classifies "poor" on 7 of 11 metrics —
  see `EVAL_FINDINGS.md`). Floor-relative framing is math-grounded
  and doesn't suffer the calibration problem.
- **Configuration vs measurement is cleanly separated.** Placement
  Criteria + Quality Preset are clearly "knobs you set"; the
  Quality card is "what you got."
- **Stacked-bar visualization is the right primitive** for repeat
  distributions — eye reads "fraction at floor" instinctively.
- **The legacy summary float is never displayed** — `assigned_schedules.score`
  is stored in the DB and exported in CSV but doesn't appear in
  the card. The card uses raw counts from `/diversity-report`,
  which sidesteps the lex-incompatibility issue with the float.

### Gaps

1. **No per-pair detail.** The endpoint returns `worst_pairs[:10]`
   with `slots: [a, b], count: n` for partners and opponents. The
   card uses only `worst_pairs.length` to count issues. Users
   can't see *which* pairs are problematic without devtools.
2. **No per-team breakdown.** The endpoint returns `slot_table`
   with per-slot distinct partners, distinct opponents, station
   distribution, surrogate count. The card uses `total_pairs` and
   `max_imbalance` aggregates and discards the per-team rows.
3. **No reference comparison.** "Avg partner repeats: 0.4, max: 2"
   doesn't tell users whether that's typical. No "comparable
   schedules average ~0.5 max 3" framing.
4. **No `/view` quality info at all.** Coaches viewing the public
   link have no diversity surface, even at a summary level.
5. **No lex-tuple breakdown.** The 8-element FRC §10.5.2 tuple is
   the canonical algorithm-level quality signal; the UI never
   surfaces it. Schedule comparison (two saved schedules, side by
   side) has no per-criterion delta view.
6. **No surrogate spread detail.** Card shows `surrogates.total`
   and `surrogates.concentrated_slots` (count). Doesn't show
   *which* slots have multiple surrogates.
7. **No SA-convergence hint.** When pairs land above floor, the
   user can't tell if math forced it or SA under-converged. A
   simple "at this preset and fixture size, more iterations rarely
   help" cue would calibrate expectations.

## Tier 1 — surface what's already on the wire

**Effort:** small (~3–4 hours, render-side only).
**Risk:** low — pure additive, no schema or endpoint changes.
**Decisions required:** none beyond layout.

The `/api/abstract-schedules/{id}/diversity-report` endpoint
already returns the data; the card just doesn't render it. Closes
gaps #1, #2, and #6.

### Sub-items

- **Surface `worst_pairs` with team numbers.** Render the top 5–10
  pairs in the Notable section as `Team 2169 × Team 4728 —
  partnered 3× (floor: 1)`. Slot→team mapping happens client-side
  using the assignment that's already loaded by the time the card
  renders.
- **Surface `slot_table` per-team detail** behind a `<details>`
  toggle inside the Quality card. Each row: team, distinct
  partners, distinct opponents, station distribution as a 6-cell
  mini-bar, surrogate count. Sortable by any column.
- **Surface concentrated surrogate slots.** When
  `concentrated_slots > 0`, list the affected teams with their
  surrogate counts so users can verify it's not unbalanced.

### Acceptance

The Notable section names specific teams when reporting issues. A
collapsed per-team table is available for users wanting full
detail. No new endpoints; no new server work.

## Tier 2 — surface the lex tuple

**Effort:** medium (new endpoint, new card section, minor backend).
**Risk:** low — additive endpoint, no schema change.
**Decisions required:** which tuple labels and explanations to
use; how to present the "structural minimum" cases.

Closes gap #5.

### Sub-items

- **New endpoint** `/api/assigned-schedules/{id}/quality-tuple`
  returning the 8-element tuple plus per-element labels and
  annotations. Calls existing `score_tuple_for_schedule()`. No DB
  changes; pure derivation from the stored matches.
- **New "Quality breakdown" section** in the Schedule Quality card.
  One row per tuple element with value, brief description, and
  status (e.g., "✓ at structural minimum" for elements that are
  always 0 in well-formed schedules).
- **Schedule comparison view** when comparing two saved schedules
  side-by-side. Per-element deltas with the FRC §10.5.2 priority
  order made explicit. Lex compare visualized — first differing
  element highlighted.

### Acceptance

The lex tuple is a first-class UI concept. Users comparing two
saved schedules can see exactly which criterion differs and by how
much. The cooldown_violations slot (always 0 in algorithm output)
is visibly marked as "structural minimum" rather than just "0" so
users understand that's a positive guarantee.

### Pre-work needed before shipping

- `match_equity` is currently hardcoded to 0 in
  `_score_from_state()` (line 1101). The tuple slot is inert.
  Either implement the construction-phase tie-breaker or drop the
  slot — see `HANDOFF.md` §5 prior-session notes on the lex tuple
  audit. Tier 2 should not ship a UI element that surfaces a
  permanently-zero value labeled as if it varied.

## Tier 3 — reference comparison via recalibrated thresholds

**Effort:** substantial (calibration data collection, threshold
tuning, distribution storage, server endpoint, UI rendering).
**Risk:** moderate — calibration involves judgment calls that
need validation before shipping.
**Decisions required:** percentile cutoffs, fixture-size
bucketing, how to handle small-fixture edge cases.

Closes gap #3. Highest user-actionable value but highest effort.

### Sub-items

- **Recalibrate `metrics.py` thresholds** against TBA-pulled
  played schedules. Infrastructure exists:
  `scripts/scheduler_eval/pull_tba_fixtures.py` and
  `event_keys.txt` listing ~20 events. Pull each event's actual
  played schedule, compute the relevant metric distributions per
  fixture-size bucket. Set `acceptable` = 80th percentile,
  `near_optimal` = 50th percentile of real schedules. Document
  the calibration data in the threshold dict.
- **Bake the calibrated distribution into a JSON file**
  (`scripts/scheduler_eval/calibration_data.json`) shipped with
  the server.
- **Server endpoint** that returns "this schedule's metric vs the
  reference distribution" — e.g., `repeat_partners=12 → 60th
  percentile of similar-size played schedules`,
  `max_color_imbalance=1 → top 10%`.
- **UI: percentile badges** next to each headline tile in the
  Quality card. "Avg partner repeats: 0.4 — 70th percentile" with
  hover for the comparison detail.

### Acceptance

A coach or organizer can finally answer "is this a good schedule?"
without knowing FRC norms. The harness's threshold framework is
finally calibrated against reality, which by itself fixes the
"MatchMaker classifies as poor" embarrassment in the harness
output (orthogonal benefit).

### Risks and open questions

- **Fixture-size bucketing.** A 24-team event has structurally
  different repeat statistics than a 72-team event. Need
  bucketing by team count and matches-per-team. Bucket boundaries
  are a judgment call.
- **Sample size.** ~20 events in `event_keys.txt` might be too
  few for tight percentile estimates in less-common bucket sizes.
  May need to pull more events before calibration is statistically
  defensible.
- **Drift over time.** As MatchMaker improves and FRC field sizes
  shift, the distribution changes. A recalibration cadence
  (annual?) needs to be defined.

This tier should not ship until the calibration work is done and
spot-checked against multiple reference fixtures.

## Tier 4 — surface to the viewer

**Effort:** small to medium depending on scope.
**Risk:** low — additive to a public surface.
**Decisions required:** whether the spectator viewer is the right
audience for quality info at all.

Closes gap #4. Independent of tier choice — any of T1/T2/T3 can
ship to `/view` as well as the editor.

### Sub-items (pick any subset)

- **Minimal: header badge.** A single-line "Schedule quality: X%
  pairs at floor, station balance: even, no back-to-backs" badge
  in the page header, computed from the same `/diversity-report`
  endpoint the editor card uses.
- **Coach-focused per-team panel.** A `<details>` panel showing a
  selected team's row from `slot_table` — partner counts, station
  spread, gap, surrogate. Requires team-selection UI in the
  viewer (it doesn't currently have one for this purpose).
- **Lex-tuple summary.** A compact rendering of T2's tuple
  breakdown, inheriting whatever the editor decides.

### Acceptance

Coaches following the public link can see whether the schedule
they're playing is reasonable. Public link → quality answer
without an account or editor access.

### Open question

Is exposing schedule-quality detail to a public audience desirable?
Pro: transparency, defends the schedule when it differs from
spectators' expectations. Con: invites litigation of edge cases
("why does my team have repeat partners 2× when others have 0?")
that are mathematically forced.

This is a product question, not a technical one. Worth deciding
before T4 ships.

## Cross-tier notes

### Effort vs. value summary

| Tier | Effort | Closes gaps                       | Decisions required        | Recommended ordering              |
|------|--------|-----------------------------------|---------------------------|-----------------------------------|
| T1   | small  | per-pair, per-team, surrogate     | layout only               | first — tightest single increment |
| T2   | medium | lex-tuple visibility              | labels, match_equity fate | second — independent of T3        |
| T3   | large  | reference comparison              | percentile bucketing      | third — gated on calibration work |
| T4   | varies | viewer parity                     | spectator-audience policy | parallel to any of T1/T2/T3       |

### Recommendation if and when this ships

T1 alone is probably the tightest single increment: ~3–4 hours of
work, 100% reuse of the existing endpoint, removes the most-
reported gap (no per-pair specifics), independent of any other
workstream.

T1 + T2 together is the natural scope for a "expose scheduler_eval
in the UI" pass. They surface real per-pair/per-team detail (T1)
and make the canonical lex tuple visible (T2) without committing
to threshold-recalibration judgment calls.

T3 is genuinely valuable but should be a separate workstream —
calibration is its own rhythm.

### Pre-work that should happen regardless

The lex-tuple audit findings from the prior session
(`HANDOFF.md` §5 prior-session notes) include three items that
become more visible if T2 ships:

- **Fix `match_equity` placeholder.** Either implement it or drop
  it from the tuple. Inert slot becomes an obvious bug if T2
  surfaces it.
- **Clarify the `score` DB column.** Document or rename to
  `summary_score` so the non-authoritative-ness is clear. Becomes
  more important when T2 makes the *actual* authoritative tuple
  visible alongside.
- **Add a cooldown verifier for imported schedules.** Independent
  of UI work but related — imported schedules currently bypass
  the SA's hard cooldown filter, so the lex tuple's index-0
  guarantee doesn't hold for them.

These were captured in the audit but not in any tracking doc until
this one. They are the low-hanging fruit that should ship before
or alongside T2.

## When to revisit

Triggers that suggest picking this work up:

1. **Users reporting "I can't tell if my schedule is good."** That's
   the gap T3 closes; T1 also helps a lot by surfacing specifics.
2. **Multi-event organizers wanting to compare schedules** across
   their season. T2's schedule comparison view solves this.
3. **Scheduler-quality regression debugging.** When a change to
   the algorithm affects schedule quality, T2's tuple breakdown
   makes the impact visible without requiring CSV exports +
   manual diff.
4. **Coach feedback during/after live events.** If post-event
   feedback says "the schedule felt unfair" without specifics, T1
   gives the data to investigate; T3 gives the framing to
   contextualize it.

Until one of these triggers, this work stays parked. Captured here
so a future session can pick it up without re-deriving the
analysis.
