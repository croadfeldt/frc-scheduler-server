# Scheduler Evaluation: Findings & Handoff

**Status**: Eval complete. **Decision: improve our in-house scheduler
to close the gap to MatchMaker.** Active workstream tracked in
[`QUALITY_IMPROVEMENT_PLAN.md`](QUALITY_IMPROVEMENT_PLAN.md).
MatchMaker is the quality benchmark; licensing prevents using it as
part of our shipped tool, so the path forward is making our scheduler
genuinely competitive rather than replacing it. This document captures
the data behind the decision and the remaining work.

**Licensing constraint**: Idle Loop's MatchMaker is "available for
evaluation purposes only. For licensing, contact us at info@idleloop.com."
The harness uses MatchMaker as a benchmark, which is permitted under
evaluation use. Distributing it as part of `frc-scheduler-server`,
running it in CI, or invoking it from production code paths is not.
See `https://idleloop.com/matchmaker/` for the source, and the
`MatchMaker Licensing Constraints — Implementation Brief` (companion
document) for the full posture and architectural implications.

**Validation strategy**: ongoing scheduler-improvement work uses the
TBA `actual` adapter as the primary validation surface — it compares
our scheduler against publicly-available played FRC schedules (which
were generated by MatchMaker via FMS for most events), giving us a
license-clean continuous validation surface. The `matchmaker` adapter
is reserved for occasional manual evaluation runs to recalibrate the
absolute quality ceiling. See `scripts/scheduler_eval/NOTICE.md` for
operational details.

**Last run**: 2026-05-09. Command was:

```
python3 -m scripts.scheduler_eval.runner \
    --fixtures all \
    --adapters frc-scheduler-server,matchmaker,actual \
    --trials 100 \
    --workers 36
```

Reports under `scripts/scheduler_eval/reports/<run-id>/` are gitignored
(harness output is per-user). To reproduce: pull the curated fixture

## TL;DR

Our in-house scheduler is significantly worse than both Idle Loop's
MatchMaker and FRC's actually-published schedules across a representative
inventory of 16 events.

| Adapter | Mean composite | Wins vs ours | Wins vs actual |
|---|---|---|---|
| matchmaker | **16.65** | 13W-0L | 5W-1L-7T |
| actual | 25.77 | 14W-2L | — |
| frc-scheduler-server | 49.29 | — | 2W-14L |

(Composite: lower is better. Computed as
`10×poor_count + 3×acceptable_count + 0.1×repeat_partners + 0.1×color_imbalance`.
A schedule with all near-optimal metrics scores 0; all-poor scores ~110.)

Our scheduler:
- Lost every fixture against MatchMaker (where MatchMaker ran)
- Lost 14 of 16 fixtures against actual published schedules
- The two "wins" against actual are weak comparisons — places where
  the published schedule is unusually bad — not signs of strength

The decision is to replace our scheduler. Integration work is tracked
separately.

### Patterns worth noting

**MatchMaker matches actual on most regional events.** When matchmaker
and actual report identical composites (10.30, 23.20, 13.20 — appearing
in 7 of 13 cases), the published schedule was almost certainly generated
by MatchMaker itself. Same algorithm, same input, same output.

**MatchMaker beats actual specifically on State Tournament events:**

| Event | MM | Actual | Gap |
|---|---|---|---|
| 2024mnst | 13.20 | 23.20 | 10.0 |
| 2025mnst | 13.10 | 30.30 | 17.2 |
| 2026mnst | 13.10 | 74.40 | **61.3** |
| 2024week0 | 10.10 | 56.40 | 46.3 |

This matches the original concern that motivated this work: **the State
Tournament schedules aren't being generated by MatchMaker.** They're
being generated by something else (presumably our scheduler in 2026
where MN State used our tool, or other tools in prior years), and the
gap is largest on the live event we just shipped.

**Our scheduler trades partner diversity for opponent diversity.**
On 2026mnst:
- Our scheduler: 4 repeat partners (better than actual's 9), but 43 repeat opponents (worse than actual's 33)
- MatchMaker: 0 repeat partners AND only 23 repeat opponents

The algorithm we have is making a tradeoff that MatchMaker doesn't
need to make. This isn't a tuning issue we can close with weight
changes — it's an algorithmic capability gap.

**MatchMaker's "12 poor" classifications overstate its problems.**
The threshold logic flags overall-poor when *any* metric is poor.
Most of MatchMaker's "poor" schedules have one cosmetic miss
(usually max_color_imbalance of 3 instead of ≤2) with everything
else near-optimal. Composite scores 10.10-13.20 are functionally
near-optimal; the binary classification is too strict for fair
comparison.

**MatchMaker is mostly deterministic.** Looking at trial distributions,
median == best for repeat_partners and color_imbalance across the 100
trials. Some variation in composite (std of 4-5) but most trials
produce identical-quality schedules. This is consistent with the
Sykes algorithm — deterministic search with light randomization.
The "best of 100" comparison is fair to MatchMaker; first-trial
results would have been nearly as good.

## Known issues / future work

### 1. Surrogate handling for odd team counts (3 fixtures still errored)

**[FIXED 2026-05-09]** Fixtures 2023mnmi (61 teams), 2024mndu (55 teams),
2025mnmi (51 teams) previously failed with `MatchMaker exited 255`. Root
cause: the adapter passed `fixture.surrogate_round` (a match number,
mislabeled as a round) to MatchMaker's `-u` flag, which expected a
1-indexed round number. Match 22 in a 9-round event isn't a valid
round, so MatchMaker rejected the configuration.

Fix: the adapter now omits `-u` entirely, letting MatchMaker use its
built-in default of round 3 (FIRST's convention since 2008). The field
on Fixture is renamed `surrogate_first_match` for clarity (it was
always a match number; the old name was misleading) and is now
descriptive metadata, not a CLI flag input. Backward-compat preserved:
`Fixture.from_json_dict` accepts old `surrogate_round` JSON keys.

Re-run the eval to populate matchmaker results for the 3 previously-
errored fixtures.

### 2. Per-metric "where each adapter struggles" view

Currently the report shows per-fixture metric tables (good) and a
cross-fixture aggregate (good), but no per-metric aggregate. A
useful addition would be:

    | Metric | matchmaker | frc-scheduler-server | actual |
    |---|---|---|---|
    | repeat_partners (% poor) | 0% | 100% | 12% |
    | repeat_opponents (% poor) | 0% | 100% | 6% |
    | max_color_imbalance (% poor) | 75% | 81% | 75% |
    | max_station_spread (% poor) | 0% | 75% | 6% |

This would let us articulate *why* our scheduler fails — which
specific metric categories. Now relevant: this view directly informs
the scheduler-improvement work since the per-metric pattern dictates
which algorithmic changes to prioritize. Estimated time: 30-60 minutes.

### 3. Verdict summary at the top of the report

A single paragraph at the top summarizing what the report shows in
plain English, derived from the data programmatically. Useful for
sharing with non-technical audiences. Estimated time: 30 minutes.

### 4. Threshold tuning for max_color_imbalance

The current threshold (≤1 near-optimal, ≤2 acceptable) is calibrated
from FRC community norms and is correct, but it makes MatchMaker's
"12 of 13 poor" classification misleading because color is a soft
constraint compared to e.g. station spread. Consider whether the
overall classification logic should weight metrics differently —
maybe "poor" requires 2+ poor metrics, not 1. Worth thinking about
but not urgent. Estimated time: 1-2 hours including re-validation
against the reviewer's numbers.

### 5. Expand fixture inventory beyond MN

Current inventory is heavily MN-weighted (10 of 13 successful
fixtures). The 4 MI championship divisions and 1 week-zero round it
out, but more variety would strengthen any future decisions. Use
`--year YYYY --state XX` expansion to add more events. Estimated
time: 30 minutes per state.

## Where our scheduler systematically fails

Looking at the per-fixture data across all 16 events, our scheduler
exhibits consistent failure patterns:

| Metric | Our scheduler | MatchMaker (where ran) | Implication |
|---|---|---|---|
| repeat_partners | poor on most fixtures | near-optimal everywhere | Algorithm fails to enforce partner diversity |
| repeat_opponents | poor on most fixtures | near-optimal where small fields, mixed otherwise | Algorithm fails to enforce opponent diversity |
| max_station_spread | poor on most fixtures (2-3) | near-optimal (0-1) everywhere | We don't have Sykes-style station balancing |
| max_color_imbalance | poor (3-5) on most fixtures | poor (3) where it fails | Both struggle, but ours is worse |
| min_match_gap | mostly OK | OK | Cooldown is enforced reasonably |
| back_to_back_matches | 0 (good) | 0 (good) | Both avoid back-to-backs |

The standout gap is **station spread**. MatchMaker uses Caleb Sykes's
algorithm (added in version 1.4, December 2021) to guarantee perfect
station balancing — every team gets the most balanced station
distribution mathematically possible (e.g. 3-3-3 for 9-round events
or 2-3-3 for 8-round). Our scheduler doesn't have this; it tries to
balance stations but ends up with spreads of 2-3 routinely.

The next gap is **partner/opponent diversity**. MatchMaker uses
simulated annealing on a score function that explicitly penalizes
duplications. Our scheduler does similar work but with different
weighting and a less sophisticated annealing schedule. The result is
a tradeoff: our scheduler picks better partner diversity at the cost
of opponent diversity, where MatchMaker gets both.

## Path forward — improving our scheduler

This work should follow the existing roadmap in
`docs/scheduler/SCHEDULER_QUALITY_ROADMAP.md` which already proposes
a phased plan (Phase 0 hard cooldown, Phase 1 R/B balance post-pass,
Phase 2 Sykes-style station balance, etc.). The eval data confirms
the prioritization concerns:

- **Phase 0 (cooldown)** is partially done in our scheduler already;
  cooldown isn't our biggest gap. Priority should be reviewed.
- **Phase 2 (Sykes station balance)** matches the biggest measurable
  gap to MatchMaker. May warrant earlier prioritization.
- **Phase 1 (R/B balance)** also relevant; both MatchMaker and our
  scheduler struggle with color imbalance, so improvements here help
  but won't differentiate us from the benchmark.

The harness will be the validation surface: as scheduler changes
ship, re-run the eval and track our scheduler's mean composite over
time. Goal: get our `frc-scheduler-server` mean composite from 49.29
into the same band as MatchMaker (16.65) and ideally beat actual
(25.77).

## Reproducing the run

```bash
# 1. Get the curated fixtures from TBA
export TBA_API_KEY=<your_key>
python3 -m scripts.scheduler_eval.pull_tba_fixtures \
    --keys-file scripts/scheduler_eval/event_keys.txt

# 2. Verify metrics module against reviewer ground truth
python3 scripts/scheduler_eval/smoke_test.py

# 3. Run the eval (matchmaker on $PATH or via MATCHMAKER_BINARY env)
python3 -m scripts.scheduler_eval.runner \
    --fixtures all \
    --adapters frc-scheduler-server,matchmaker,actual \
    --trials 100 \
    --workers 36

# 4. Read the report
cat scripts/scheduler_eval/reports/<latest>/report.md
```

The `2026mnst` fixture and its `__actual.json` are tracked in the
repo and don't need re-pulling. Other fixtures are gitignored — the
TBA fetcher regenerates them on demand.
