## Why this document exists

The three-layer architecture catalogs algorithm suites including ones in the "MatchMaker family." Before any code is written that bundles, calls, or distributes MatchMaker itself, the implementing session needs to know exactly what's permitted and what isn't. This brief establishes the hard line so design choices stay on the right side of it.

**Bottom line up front:** the project will reimplement the published Saxton-Sykes algorithm independently, will not bundle or call the MatchMaker binary, will not redistribute MatchMaker artifacts, and will validate its output against historical FRC event data (via TBA) rather than against live MatchMaker runs. This is Path A in the discussion that produced this brief.

## The licensing facts

Sourced from `idleloop.com/matchmaker/download.php` and the site's footer (verified May 2026):

> "These programs are available for evaluation purposes only. For licensing, contact us at [info]."

> "©2000-2026 Idle Loop Software Design, LLC. You may not copy or reproduce any content from this site without our consent."

This is proprietary, evaluation-only licensing. Three implications matter for our work:

1. **Non-profit use is not exempted.** The license language draws no distinction between commercial and non-profit use. Both require explicit permission beyond evaluation.

2. **"Evaluation purposes only" is narrow.** It permits a single user running MatchMaker locally to assess whether to license it. It does not permit redistribution, bundling, hosting, or making MatchMaker's output available as a service to third parties.

3. **Algorithm ideas are not protected; specific code and binaries are.** The published white paper at `idleloop.com/matchmaker/index.php` and the Sykes station-balancing description at `idleloop.com/matchmaker/stations.php` exist precisely so the algorithm can be discussed, taught, and independently implemented. That's a separate question from copying or wrapping the binary.

## Hard rules for the implementing session

### Do NOT do any of these

These are bright-line prohibitions. If a design proposal requires any of them, stop and surface it before writing code.

1. **Do not bundle the MatchMaker binary** in the repo, in container images, in release artifacts, or in any installer. This is redistribution and is not permitted.

2. **Do not invoke MatchMaker as a subprocess** from any code path that runs in production, in a hosted service, in CI, or in any user-facing feature. The "evaluation only" line excludes use as a service backend.

3. **Do not auto-download the MatchMaker binary** at install time, build time, or runtime. Hosting elsewhere does not change the legal substance — fetching and executing on behalf of a user constitutes use beyond evaluation.

4. **Do not name an algorithm suite "MatchMaker"** in code, UI, configuration, or marketing. The trademark and brand belong to Idle Loop. Use descriptive names that credit the *technique* without claiming the *brand*.

5. **Do not copy code from MatchMaker's binary, decompiled output, or any leaked source** even if it appears on Chief Delphi or elsewhere. Independent implementation from published descriptions only.

6. **Do not represent the tool's output as MatchMaker output** even when the algorithm is faithfully reimplemented. Output provenance must say what it actually is.

### DO these instead

1. **Reimplement the Saxton-Sykes algorithm independently** from the published white paper and Sykes station-balancing description. This is Path A and is fully permitted.

2. **Credit the inspiration explicitly.** In the algorithm suite documentation, in `PRIORITIES.md`, and in the schedule provenance, attribute the algorithmic approach to Tom and Cathy Saxton (Idle Loop Software Design) and Caleb Sykes. Link to `idleloop.com/matchmaker/`. Make clear our implementation is independent.

3. **Use TBA event data as the validation baseline.** Past FRC qualification schedules are public record via The Blue Alliance API. Those schedules were generated by MatchMaker via FMS. Comparing our tool's output to TBA-fetched schedules compares against public event records, not against a copy of MatchMaker. This is the legally clean way to do the comparison harness.

4. **Allow users to compare against their own MatchMaker runs.** If a user has separately downloaded MatchMaker for evaluation, they can run both tools on the same input and import both schedules into ours for comparison. The tool can accept a CSV import of an externally-generated schedule and produce diff metrics. We never run or distribute MatchMaker; the user does, on their own machine, under their own evaluation.

## Validation harness — TBA-based design

This replaces the "MM comparison harness" framing in the original roadmap. The validation strategy uses public FRC event data, not live MatchMaker runs.

### What the harness does

1. **Fetches a corpus** of qualification schedules from past FRC events via the TBA API. Target: 20–30 events spanning a range of (N, MPT) values. These schedules were generated by MatchMaker via FMS; they are MatchMaker's output by definition.

2. **Computes diversity metrics** on each fetched schedule using our tool's metrics extractor — partner-repeat distribution, opponent-repeat distribution, station balance, alliance balance, surrogate distribution, gap statistics. This treats TBA schedules as ground truth.

3. **Generates schedules** with our `sa-saxton-sykes-extended` algorithm at matching parameters (N, MPT, cooldown derived from event size) for each event in the corpus. Computes the same metrics.

4. **Produces a comparison report** showing per-metric deltas between the TBA baseline and our output. The report goes in `tests/validation/` as a committed artifact.

5. **Runs as CI** on a nightly schedule. Regression alerts if any metric drifts more than 5% from the established baseline.

### What this gives us

- **Empirical validation** that our `sa-saxton-sykes-extended` suite produces schedules of comparable quality to MatchMaker, *without ever running MatchMaker*.
- **A defensible "FIRST-aligned" claim** in `PRIORITIES.md`. The claim is grounded in measured comparison against the corpus of actual FRC events, not against design intent.
- **A regression detector** so future changes don't silently degrade quality.
- **Zero licensing exposure.** TBA data is public record. Our reimplementation is independent. The comparison is between our output and public records.

### What this does NOT give us

- **Optimality claims for individual schedules.** We cannot say "MatchMaker would have produced exactly this schedule." We can only say "our schedule's metrics fall within the distribution of MatchMaker-generated schedules from real FRC events at this size."
- **Bug-for-bug compatibility.** If MatchMaker has a quirk we haven't reproduced, the harness might flag it as a difference. That's fine — we're not aiming for bug compatibility, we're aiming for *quality parity*.
- **Live "what would MatchMaker do here?" answers.** A user asking that question runs MatchMaker themselves. We don't proxy.

### Implementation skeleton

Roughly:

```
tests/validation/
  corpus/
    {event_key}/
      tba_schedule.json       # fetched once, committed
      our_schedule.json       # regenerated by harness
      comparison.json         # per-event diff
  fetch_corpus.py             # TBA API → corpus/
  run_harness.py              # generates our schedules, computes diffs
  baseline.json               # current accepted metric ranges
  SUMMARY.md                  # human-readable report
```

The corpus is committed (or cached in CI) so the TBA API isn't hit on every run. Re-fetching is a deliberate maintenance task.

## What about a user-supplied MatchMaker import?

Permitted and worth supporting as an optional feature.

A user who has independently downloaded MatchMaker (under Idle Loop's evaluation license, on their own machine) can run it on their event roster, get a schedule, export it as CSV, and import it into our tool for comparison or analysis. Our tool's responsibility:

- Accept a schedule CSV import. Parse it. Compute diversity metrics on it. Display side-by-side with our tool's output.
- Never bundle, host, or invoke MatchMaker ourselves.
- Be clear in the UI that the import is the user's responsibility — they are running MatchMaker under their own license.

This gives power users the head-to-head comparison they might want, without putting our project on the wrong side of the license line. The legal posture is: *our user evaluated MatchMaker themselves; we just accept any schedule CSV regardless of source.*

If implementing this, the import path should be generic — accept any schedule CSV, not specifically a MatchMaker-formatted one. Other tools produce schedules too; we accept them all and don't single out MatchMaker in the import UI.

## What's NOT being decided in this brief

- **Whether to ever reach out to Idle Loop for a license.** That's a future decision Chris controls. If we ever want to bundle the binary or invoke it as a service, we ask. For now we don't need to.
- **Whether to engage with Caleb Sykes about the station-balancing algorithm.** His description is published; reimplementing from it is fine. Crediting him in documentation is required (see naming guidance). Beyond that, no engagement is needed.
- **Sanctioning body submission.** Whether our `frc-2026` criteria suite ever gets reviewed or endorsed by FIRST is a separate, much larger conversation. The technical work to be FIRST-aligned is necessary but nowhere near sufficient for that.
- **Trademark guidance for the project name itself.** "FRC Scheduler" is descriptive and unlikely to conflict with anything. If marketing changes the project name, that's a separate review.

## Quick-reference checklist for implementers

When writing code for any algorithm suite, post-pass, or validation feature, check:

- [ ] Are we copying any MatchMaker code, binary, or output? → **STOP, not allowed.**
- [ ] Are we invoking any MatchMaker process? → **STOP, not allowed.**
- [ ] Are we bundling any MatchMaker artifact? → **STOP, not allowed.**
- [ ] Are we naming a suite or feature "MatchMaker"? → **STOP, rename.**
- [ ] Are we implementing from the published white paper or Sykes description? → **OK, proceed with attribution.**
- [ ] Are we comparing to TBA-fetched event data? → **OK, proceed.**
- [ ] Are we accepting user-imported schedule CSVs? → **OK, proceed; keep the import path generic.**
- [ ] Are we crediting Saxton, Sykes, and Idle Loop in the suite documentation and provenance? → **Required; verify before merging.**
